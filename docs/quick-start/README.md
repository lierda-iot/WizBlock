# Quick Start：display_demo

[中文](README.md) | [English](README.en.md)

目标：在 ESP32-S3 L-AIWFS300 核心板连接 ST7789V3 屏幕板后，构建并运行 `display_demo`，观察白、红、绿、蓝依次全屏显示，每种颜色保持约2秒。

状态说明：2026-06-12 的历史实机证据只覆盖白色和红色填色；当前四色源码于2026-08-31完成Windows当前维护环境clean build，但尚未完成当前源码的四色实屏复核。现有已验证构建脚本含本机配置且不进入公开候选；跨机器公开入口留到最终S5，本页当前是Quick Start草案。

当前定位：**维护者构建复现指南 + 外部阅读型预览 + 功能验收清单**。本文不承诺外部用户可直接执行构建或烧录，也不提供公开烧录命令；它负责把当前维护者构建证据、完整烧录流程和功能验收口径放在一条可阅读、可对照的路径中。

## 1. 准备

- L-AIWFS300 A0 核心板与匹配屏幕板。
- 可传输数据的 USB-C 线和稳定供电。
- CH340E 串口驱动；设备管理器或 `/dev/cu.*` 能看到新串口。
- Git。
- ESP-IDF v5.5.4；激活后 `idf.py --version` 可用。
- 把仓库 clone 到较短的 ASCII 路径；仓库地址使用后续正式发布地址替换 `<repository-url>`。

```bash
git clone <repository-url> <short-ascii-path>
cd <short-ascii-path>
```

## 2. Windows 当前维护环境入口

先在私有事实源仓库根目录的Git Bash中完成完整镜像：

```bash
rm -rf "$TEMP/laiwfs300_build/CODE"
mkdir -p "$TEMP/laiwfs300_build"
cp -r "./CODE" "$TEMP/laiwfs300_build/CODE"
```

然后在仓库根目录的PowerShell中相对调用既有脚本：

```powershell
& "./CODE/tools/build_example.ps1" -Example display_demo -Clean
```

该入口符合设计4.1.2，2026-08-31复验在170.4秒内退出0并完成`1421/1421`。脚本含维护者ESP-IDF绝对路径，保持不修改且不进入公开候选；它只说明当前维护环境如何复现既有证据。外层`build_example.sh`本轮未在200秒内正常返回，不作为通过入口。

## 3. macOS 当前已验证入口

在私有事实源仓库根目录执行：

```bash
cd ./CODE
bash ./tools/build_example_macos.sh display_demo clean
```

该入口曾在macOS完成`display_demo` clean build，但脚本含维护者环境假设，保持不修改且不进入公开候选；当前候选尚未在新的macOS环境复核。

## 4. 当前公开定位与边界

公开候选不包含上述维护者脚本，也没有通过验证的跨机器构建命令。外部读者当前可以：

1. 阅读`display_demo`源码、硬件说明和当前验证状态。
2. 理解维护者在Windows/macOS复现clean build所采用的入口和证据边界。
3. 阅读下方完整烧录流程，并与`open-flash`及共享流程契约逐项对照。
4. 使用功能验收清单检查后续人工构建、烧录和实机记录是否完整。

现阶段不要求在公开候选中提供可执行烧录方法。本文不会拼装直接`idf.py`、esptool、固定端口或维护者绝对路径命令；当调用Skill执行烧录而公开可移植入口尚不存在时，应返回`S5_PORTABLE_ENTRY_PENDING`。未来最终S5若增加跨机器入口，仍需单独完成Windows/macOS验证，不能反向把当前阅读型预览描述为已执行通过。

## 5. 完整烧录流程（阅读与实现对照）

以下是流程契约，不是可复制执行的烧录命令：

1. **锁定输入**：明确仓库版本、目标Example为`display_demo`、平台和本次产物集合，不继承聊天中的隐含状态。
2. **检查成功构建证据**：确认同一仓库版本、同一Example和同一平台的clean build已经成功，并记录产物位置与结果；构建失败立即停止。
3. **发现并明确端口**：只枚举当前串口候选，不使用历史端口。无候选时阻塞；多个候选时等待用户选择；即使只有一个候选也不能自动取得设备写入权限。
4. **确认目标设备**：由用户核对端口、板卡型号和板卡角色，避免向错误设备写入。
5. **说明擦除影响**：显示本次流程是否包含全片擦除，并明确全片擦除会清除设备内已有程序、配置和持久化数据。
6. **取得设备写入确认**：在真正写入前取得本次、当前设备、当前端口的明确确认；旧授权或单一端口都不能代替本次确认。
7. **执行一次完整写入流程**：按对应Example已验证的维护者入口依次完成全片擦除、程序写入和Hash校验；不在本文公开具体命令。
8. **分层记录结果**：分别记录擦除结果、各分区/镜像写入结果、Hash校验和复位结果。烧录失败时停止在首个错误，不自动重试、重复擦除、切换端口或更换工具。
9. **复位并观察启动日志**：确认设备退出下载态并进入应用启动；端口占用或下载态问题优先按复位/串口流程处理，不用重复烧录代替诊断。
10. **执行功能实机验收**：只有屏幕、串口日志和稳定性检查全部满足下一节清单，才能记录功能实机通过。

实现对照入口：

- [`open-flash` Skill](../../skills/open-flash/SKILL.md)：输入、端口选择、设备确认、写入门禁、失败停止和结果字段。
- [Skill流程契约](../../skills/references/workflow-contract.md)：依赖传播、确认门和最终S5边界。
- [Skill状态契约](../../skills/references/status-contract.md)：`PASS`、`FAILED`、`BLOCKED`和`NEEDS_USER`等结果含义。
- [开发流程](../development/workflow.md)：明确端口、必要全片擦除、烧录校验、启动日志和可观察行为的顺序。

## 6. 功能验收清单

三类证据必须分开记录，不能互相替代：

| 证据层级 | 至少记录 | 能证明 | 不能证明 |
| --- | --- | --- | --- |
| 构建证据 | Example、平台、clean build结果、产物 | 固件已生成 | 已写入设备或功能正常 |
| 烧录证据 | 目标设备与明确端口、全片擦除、各镜像写入、Hash校验、复位 | 本次产物已被正确写入目标设备 | 屏幕、日志和长期运行符合预期 |
| 功能实机证据 | 启动日志、四色顺序、保持时间、异常扫描和人工观察 | 本轮可观察功能是否通过 | 其他Example或未覆盖功能也通过 |

`display_demo`功能实机通过需要同时满足：

1. LCD 初始化成功。
2. 屏幕按白、红、绿、蓝顺序循环，每种颜色保持约2秒。
3. 串口按相同顺序输出`fill: white`、`fill: red`、`fill: green`、`fill: blue`。
4. 无 panic、assert、Task WDT 或异常复位。

构建通过只证明固件生成；只有实际烧录并观察到上述屏幕与日志行为，才算功能实机通过。

当前证据边界：2026-06-12历史实机只覆盖白色和红色；2026-08-31当前四色源码clean build通过，当前四色完整实机清单仍待复核。

## 7. 失败时

- 维护环境脚本找不到ESP-IDF：按`design.md`记录修复同一v5.5.4环境，不切换未知runner。
- 源码改动未生效：重新执行完整脚本入口，不能跳过其中的全量镜像和clean build。
- Windows非ASCII路径异常：确认使用现有Git Bash脚本入口，不用`Copy-Item`替代镜像。
- 找不到端口：检查数据线、CH340E 驱动、USB权限和设备供电。
- 屏幕黑屏：先核对板卡连接、电源和串口初始化错误；不要用重复烧录代替硬件检查。

更多信息见[故障排查](../troubleshooting/README.md)。

## 8. 三种阅读路径

- 维护者复现构建：按第1～3节确认环境并复用既有脚本，再按第6节只记录构建证据。
- 外部阅读预览：阅读第1、4、5节，理解当前公开边界与完整烧录流程；不得把流程描述当成已提供命令。
- 功能验收复核：按第5～7节逐项检查烧录证据、启动日志和四色行为，任一层缺失都不得宣称完整通过。
